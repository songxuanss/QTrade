# QTrade 安全、风险与合规要求

## 1. 安全基线

### 身份与会话

- 只使用 SSO 登录，QTrade 禁止本地密码认证。
- Authorization Code + PKCE。
- HttpOnly、Secure、SameSite cookie。
- CSRF token 保护所有状态变更请求。
- state / nonce 一次性使用并设置 TTL。
- Back-channel Logout 立即撤销本地会话。
- 敏感操作二次认证或重新认证可后续启用。

### API 权限

- 后端必须做对象级授权，不能只依赖前端隐藏按钮。
- 每个请求记录 `actor`、`workspace`、`action`、`resource`、`trace_id`。
- 默认 deny，权限显式授予。
- API token 与 SSO 会话分开，支持 scope、过期、轮换、撤销。

## 2. 密钥与凭证管理

### 必须实现

- Broker / Exchange API key 加密存储。
- 密钥写入使用 envelope encryption。
- 生产密钥不可明文返回，前端只显示掩码和最后四位。
- 密钥变更、删除、测试连接全部审计。
- 支持只读 key 与交易 key 分离。
- 测试网 / 只读验证通过后才允许实盘 key 绑定。

### 建议

第一期可用 PostgreSQL + KMS / SOPS 管理 root key；二期引入 HashiCorp Vault 或云 KMS。

## 3. 交易风控

### 预交易检查

每个订单必须通过：

1. 用户是否有交易权限。
2. 策略是否处于 approved / live 状态。
3. 市场是否开放。
4. 标的是否允许交易。
5. 价格是否偏离参考价超过阈值。
6. 数量、金额、精度是否符合规则。
7. 是否重复请求。
8. 频率限制。
9. 持仓、名义本金、杠杆、集中度限额。
10. 单日亏损与最大回撤限额。
11. kill switch 状态。

### 熔断规则

| 触发 | 动作 |
| --- | --- |
| 单日亏损超限 | 拒绝新订单，通知 risk_manager |
| 最大回撤超限 | 暂停策略，可选撤销未成交订单 |
| 数据延迟超限 | 禁止依赖该数据的策略下单 |
| 券商对账失败 | 暂停策略并要求人工处理 |
| 连续拒单 / 异常成交 | 自动进入冷却期 |
| 全局 kill switch | 拒绝所有新订单，仅允许平仓或管理员操作 |

### 实盘发布

策略必须满足：

- 代码版本已审查。
- 静态检查通过。
- 回测报告已保存。
- Paper trading 至少运行 N 个交易日且无严重异常。
- risk_manager 审批。
- 实盘限额配置完成。
- 回滚和暂停方案明确。

## 4. 审计

必须审计：

- 登录、登出、登录失败。
- 工作区与权限变更。
- 策略创建、修改、发布、暂停、归档。
- 回测输入与结果访问。
- 数据源和密钥配置。
- 风控规则修改。
- 订单创建、修改、撤销、成交、拒绝。
- kill switch 操作。
- 对账与异常处理。

审计日志不可由普通用户修改或删除，建议 WORM 存储。

## 5. 数据安全与许可

- 明确行情、基本面、另类数据供应商授权范围。
- 记录每个数据集 license、保留期限、可分享范围。
- 用户偏好、策略代码、密钥、订单数据分表分权限。
- 原始数据、清洗数据和衍生数据保留血缘。
- 生产数据导出需要审批与脱敏策略。

## 6. 工程安全

- 依赖扫描、SBOM、镜像扫描。
- 静态代码扫描与 secret scanning。
- 策略沙箱限制 CPU、内存、网络、文件系统、执行时间。
- Web、API、worker、engine runner 分容器权限。
- 数据库、对象存储、Redis 不直接暴露公网。
- 生产环境只使用 HTTPS。
- 备份加密并定期恢复演练。

## 7. 合规注意

不同市场对程序化交易、投资建议、代客交易、杠杆、加密资产和跨境数据传输有不同要求。开始商业化或接入真实资金前，应完成：

- 目标市场监管评估。
- 用户协议、风险披露、免责声明。
- 交易权限与账户归属。
- 数据再分发许可。
- 反洗钱 / KYC 是否适用。
- 审计留存周期。
- 算法交易报备或交易所 API 规则。

本文档只做工程治理提示，不构成法律意见。
