# Design

## Context

现有HistoricalSource支持来源/授权/周期及可选最早日期；底层Worker可以注册多个Provider，但composition只注册MaiRui，单标的与campaign预览仍固定供应商字符串。研究发布依赖版本化Bar转换与质量报告。独立采集core/PG已拥有股票池和聚合计划，归档与行情仍经兼容Adapter。见proposal.md的动机；目标字典见docs/data/MULTI-SOURCE-DATA-DICTIONARY.md。

## Goals / Non-Goals

目标：来源选择集中注册，Provider映射知识留在Adapter；通用能力与证据描述独立发行；来源加入不会将供应商SDK散布到策略、交易或UI。首轮实际下载仍以已支持的Bar类目展开，其他类目按契约逐步实施，未实现时明确禁用。

非目标：不把所有新类型塞进Bar，不在本次采购数据，不用静默fallback保证虚假的完整覆盖；未有供应商账号时只建立禁用配置入口，不声称完成源集成。

## Decisions

1. 类目与字段schema从独立data-contracts定义，公开能力通过通用目录返回；原始来源记录不变，mapping_version定义标准化。QuoteSnapshot/TradeTick/OrderEvent分开。仅增加granularity无法表达不同市场事实，因此不能继续只按tick枚举统一处理。
2. 使用小Interface供调用方获得能力并按冻结选择建计划；Adapter负责标识、单位、时点和错误翻译。QTrade composition组装注册表与现有执行接口；core不认识厂商或WorkspaceAccess。相比UI分支和散落开关，注册表使限额、权限与转换版本有单一维护位置。
3. 能力表保存declared与observed证据、最近检查、市场/类目/周期、字段、范围限制和权限状态。最早日期允许unknown并按标的验证，不能一个日期推断所有股票。证书轮换不改变旧产物；授权身份/能力版本可更新而凭证不可进入契约。
4. 缺失计算新增来源与语义身份；现有已冻结MaiRui计划使用原来源，旧Dataset ID不变。跨源并存及对账只生成新引用，不覆盖旧价格。另一源重下载必须独立计划，不能自动补入原manifest。
5. 首轮复核正式版MaiRui；RQData为商业主源优先候选，Tushare为低成本日频候选。无账号仍保持未连接。商业样本验收按相同字段、异常与历史时点集比较，不以官网宣传创建可靠性评分。授权或来源异常用安全错误码，具体第三方响应不公开。
6. `.env`私有0600、Git ignore持久配置符合用户已有授权；只记录新配置是否加载。部署API/Worker共同更新，避免旧Worker继续用旧证书。配置开关不能提升实际付费权益。

## Risks / Trade-offs

- 文档宣称与真实质量差异→文档/样本/e2e证据分级；连续运行才形成可靠性证据。
- 财报更正、不同复权算法导致未来数据→保留公告与修订，统一基准并冻结输入；无法证明PIT则限制用途。
- 大池吞吐与套餐限制→来源级配额、受控预检、七天有界展开、可查询退避与失败；新证书重新验收而非修改历史证据。
- 一个供应商范围未包括北交所/退市→市场分别记录，不把沪深覆盖叫全A股。
- 全类别一次实施扩大范围→字典完整但任务按参考、Bar、公司行为、PIT和微观结构分期；每种类型真实验收后才开放。

## Migration Plan

先提交字典、正式证书能力报告及注册表契约，增加新字段保持旧manifest兼容；从单标的验证到整池UI，正式版实际范围分项验收。源选择灰度开放，未配置/失败能力禁用。后续供应商采用同一套质量与端到端测试，关闭新源可回退，已完成产物不删除或改写。原portable变更的远程迁移/outbox等任务继续保留，不由本变更宣称完成。
